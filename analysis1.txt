## 1. Problem Statement

Before a scene is greenlit or scheduled, someone on the production has to manually answer two questions for every scene that touches the real world:

1. **Is this factually/legally sound?** Does the scene reference a real place, historical event, law, government building, technical process, or brand in a way that's inaccurate, legally risky (e.g. depicting a real living person or institution unfavorably, needing a permit for a real government building), or just embarrassingly wrong (e.g. currency, dates, defunct organizations)?
2. **Where could we actually shoot this?** If the scene describes a setting rather than naming a real place ("an abandoned Soviet radar station," "a coastal fishing village"), what real, currently-accessible locations plausibly match it?

Today this is done manually — a script supervisor, researcher, or junior member of the writers' room searches the web scene-by-scene. This is slow (est. 30–90 min per scene with meaningful real-world content), inconsistent (depends on who's doing it and how thorough they are), and easy to skip under deadline pressure — which is exactly when legal/continuity errors make it to set or to the final cut.

**This is a real bottleneck in the "development/pre-production" stage of the entertainment value chain**, squarely in the filmmakers/screenwriters/studio-crew lane the hackathon targets.

## 2. Goals

- Cut first-pass fact/location research time per scene from ~30–90 minutes to under 2 minutes of agent runtime plus a few minutes of human review.
- Produce output that is *directly usable*, not just a chat answer: a structured, cited brief that can be filed, searched, and handed to legal or the locations department without rewriting.
- Ground every factual claim in **live, current web data** — not the model's training data — since screenwriters invent plausible-but-wrong details constantly and locations' real-world accessibility changes over time.
- Ship as a real, callable agent: usable via a web UI/API today, and registerable as a no-code tool inside Vertex AI Agent Builder for non-technical production staff.

### Non-goals (v1)

- Not a full script-coverage tool (story structure, character arcs, marketability scoring) — scoped strictly to factual/location/continuity verification.
- Not a legal-clearance system of record — it surfaces risk and open questions, it does not replace a clearance attorney's sign-off.
- Not doing actual permit filing or location booking — it identifies candidates and flags what's needed, a human/locations team takes it from there.
- No fine-tuning; v1 uses prompting + structured output only.

## 3. Target Users & Use Cases

| User | Use case |
|---|---|
| **Screenwriter** | Paste a new scene while drafting to sanity-check any real-world claim before it goes further ("did I get the year the Berlin Wall fell right?"). |
| **Script supervisor** | Batch-run an entire script/episode ahead of a table read to produce a continuity/fact-check log. |
| **Location manager** | Get a first pass of real candidate locations matching a written setting, with access/permit notes, before committing scouting-trip time. |
| **Studio legal/compliance (secondary)** | Receive the "open questions" and "production risk" sections as a triage list of what needs formal legal review. |

## 4. User Stories

1. *As a screenwriter*, I paste a scene and get back a list of every checkable claim in it, each marked confirmed/contradicted/unverified with a plain-language explanation and sources, so I can fix wrong details before the table read.
2. *As a script supervisor*, I run this against a full episode PDF and get one consolidated report I can attach to the production bible.
3. *As a location manager*, I read a scene's setting description and get 2–4 real candidate locations with region and access notes, instead of starting a web search from scratch.
4. *As a producer*, I see an "open questions" list surfaced automatically (e.g. "scene depicts a real currently-operating courthouse — confirm we have/need permission") so nothing legally risky slips through silently.

## 5. Functional Requirements

### 5.1 Input
- FR-1: Accept a scene or script excerpt as raw text (v1), via the web UI, the `POST /brief` API, or Agent Builder chat.
- FR-2: (Stretch) Accept a full script PDF and process it into one brief per scene, using the Document Processing patterns already in the hackathon resource set.

### 5.2 Claim extraction
- FR-3: The agent must identify every claim in the following categories: `historical_fact`, `location_detail`, `legal_or_permit`, `technical_or_scientific`, `brand_or_ip`, `continuity`.
- FR-4: Each extracted claim must retain a `scene_reference` (scene number/slugline) so findings can be traced back to the script.

### 5.3 Verification (Parallel integration — the core requirement)
- FR-5: For every extracted claim, the agent must call Parallel's `web_search` tool (via `parallel-google-adk`) with a focused objective and 2–3 keyword queries, and may call `web_fetch`/`extract` to read specific promising sources in depth.
- FR-6: Every claim must be assigned a `verification_status`: `confirmed`, `partially_confirmed`, `contradicted`, or `unverified`. The agent must not fabricate sources — only URLs actually returned by Parallel's tools may be cited.
- FR-7: The agent must not silently resolve ambiguous legal/rights questions — anything requiring human judgment goes into `open_questions`.
- FR-8: `ParallelTracingPlugin` must be attached at the Runner level so every Parallel tool call (latency, citation count, cost) is auditable after the fact — both for debugging and as runtime-usage proof for judging.

### 5.4 Location candidate generation
- FR-9: For scenes with a described (non-named) setting, the agent must search for and return 2–4 real candidate locations with `region`, `why_it_fits`, and `permit_or_access_notes`.

### 5.5 Output
- FR-10: Output must conform to the `ContinuityBrief` Pydantic schema (see `schemas.py`) — structured JSON, not free text — so it can be piped into other systems (Sheets, Slack, a production tracker) without additional parsing logic.
- FR-11: Output must include a short human-readable `generated_summary` (2–4 sentences) for a skim-read by an EP or script supervisor.

### 5.6 Deployment & access
- FR-12: The agent must be deployable to Vertex AI Agent Engine as a managed, callable service.
- FR-13: The agent must also be exposed as a real **web** front end (Cloud Run + `static/index.html`), satisfying the contest's platform requirement, and additionally registerable as a custom tool inside Vertex AI Agent Builder using Service Agent ID Token auth for non-technical staff.

## 6. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Latency | Single-scene brief in under ~60–90 seconds (bounded by number of claims × search calls) |
| Cost | Runs comfortably within Parallel's free-tier signup credit ($20–80) for demo/dev use |
| Reliability | If Parallel's API is unreachable, the agent should degrade to returning `unverified` status with a note, not fail the whole request |
| Security | Parallel API key stored in Secret Manager, never hardcoded; Cloud Run service not publicly unauthenticated in production |
| Auditability | Every claim's cited sources must be traceable — no citation without a real returned URL; `ParallelTracingPlugin` trace retained per run |
| Observability | Agent Engine tracing enabled (`enable_tracing=True`) for debugging tool-call chains |

## 8. Data Model (summary — full detail in `schemas.py`)

- `ContinuityBrief`
  - `scene_title: str`
  - `generated_summary: str`
  - `claims: List[ScriptClaim]`
    - `claim_type`, `scene_reference`, `claim_text`, `verification_status`, `finding_summary`, `sources: List[SourceRef]`, `production_risk`
  - `location_candidates: List[LocationCandidate]`
    - `name`, `region`, `why_it_fits`, `permit_or_access_notes`, `sources`
  - `open_questions: List[str]`

## 9. Key Prompt/Agent Behavior Decisions

- The system instruction forces the model to treat claim verification and location research as **tool-driven**, not knowledge-driven — it must call Parallel before asserting a status, rather than answering from memory.
- `output_schema=ContinuityBrief` on the ADK `LlmAgent` forces structured final output, removing the need for a separate parsing/extraction pass.
- The agent is instructed to keep `finding_summary` short (2–3 sentences) to keep the brief skimmable rather than turning into a research dump.

## 10. Success Metrics (for demo/judging)

- **Functional demo**: live call against a real scene, showing an actual Parallel `web_search`/`web_fetch`/`extract` call and a `ContinuityBrief` with real cited URLs (not mocked).
- **Time saved (qualitative)**: side-by-side of "manual search time for this scene" vs. agent runtime.
- **Correctness spot-check**: at least one deliberately-planted factual error in the demo scene (e.g. wrong currency/date) that the agent correctly flags as `contradicted`.
- **Partner integration depth**: `web_search`, `web_fetch`, and `extract` all demonstrably invoked via the official package, with the tracing plugin's output shown as proof.

## 11. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Model asserts a verification status without actually calling the tool | System instruction explicitly requires a tool call per claim; can add a lightweight post-check that every `confirmed`/`contradicted` claim has ≥1 source, else force `unverified` |
| Parallel API quota/cost during heavy demo/testing | Free signup credit ($20-80) plus a $5/month free tier available; usage is light per brief |
| Hallucinated citations | Explicit instruction: only cite URLs returned by tool calls; schema requires `SourceRef` objects, not freeform text |
| Legal false confidence | `open_questions` field exists specifically so the agent flags rather than resolves ambiguous legal/rights matters |
| Long scripts exceed reasonable single-call scope | v1 scopes to one scene/excerpt at a time; full-script batching is an explicit stretch goal (FR-2), not a v1 blocker |
| Submission disqualified on a technicality (license, platform, AI-vendor rule) | See Section 13 — compliance mapped explicitly against the Official Rules |
